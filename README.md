# 稽核代码

项目按“稽核项”组织。每个稽核项包含一份字段提取代码和一份稽核规则代码，两者使用同一编号配对。

## 单系统解析与稽核平台

本地平台一次只接收一个业务系统子文件夹，不扫描同部门的其他系统。页面会依次完成：

1. 解析当前系统文件夹里的全部受支持材料；
2. 自动运行当前注册的全部稽核项；
3. 分别显示通过、不通过、不适用、人工复核、缺文档和解析异常；
4. 保存每项字段 JSON、稽核 JSON、统一汇总 JSON 和独立离线 HTML 报告。

### 首次安装与启动

发布包不依赖固定用户名、桌面目录或安装位置。将整个文件夹复制到任意位置后，双击
`启动稽核平台.command` 即可：

- 首次运行自动检测 Python 3.11～3.14；缺失时通过 Homebrew 在线安装 Python 3.12。
- 自动检测 LibreOffice；缺失时通过 Homebrew 在线安装。
- 在程序目录生成独立 `.venv`，在线安装网页服务、anydoc、OCR、PDF和图片处理依赖。
- `frontend/dist` 已存在时不需要 Node.js；只有发布包漏掉网页构建文件时才会自动安装
  Node.js并重新构建。
- 环境安装完成后自动启动服务并打开浏览器。以后再次双击只做快速检查，不会重复安装。

安装脚本使用自身所在目录定位 `app.py`、`parser` 和 `.venv`，不会写死发送者电脑的路径。
如果 macOS 阻止首次打开，请在访达中右键该脚本并选择“打开”。

也可以在终端运行：

```bash
cd "/任意位置/浙江移动-定级备案报告稽核系统"
./启动稽核平台.command
```

浏览器访问 `http://127.0.0.1:8765`。输入必须是类似下面的最小业务系统文件夹：

```text
/资料目录/网络安全部/某业务系统-2
```

首页可点击“选择文件夹”打开 macOS 原生目录选择窗口，也可以直接粘贴绝对路径。
结果列表的“中间提取内容”栏会直接显示每个稽核项提取到的字段和值；点击稽核项后，详情页会展示完整字段内容，较大的资产记录只在列表显示条数、在详情中完整展开。

平台结果保存在 `output/单系统/<系统名>-<路径哈希>/`。同一路径再次运行时，只在新任务完整结束后替换上次结果；取消或程序中断不会破坏已有结果。原始材料目录始终只读。

### 统一模型分析

网页任务会按稽核编号逐项执行“字段提取 → 业务判断 → 模型分析 → 完成事件落盘”。
只有模型步骤返回后，该项完整结果才会写入任务事件文件；前端持续监听这个文件，并按
落盘顺序独立播放，不会反向阻塞后台。所选模型会基于本项提取字段和证据，直接以第一人称
自然说明核对过程、判断理由和最终结论，不额外显示报告式段落标题。通过、不通过和不适用的状态仍受业务计算约束，
模型不会改写状态；调用失败也不会改变结论或阻止后续
稽核项继续执行。缺文档、缺章节、多文档冲突或提取异常的项目也会经过模型步骤，再将
规则原因和模型说明作为同一个完整结果落盘。

首次使用时，在网页右上角打开“模型配置”，填写已轮换的新 API Key，并选择或输入模型编码。全系统共用同一个模型配置：

```text
Base URL: https://open.bigmodel.cn/api/paas/v4
Model: glm-5v-turbo 或 glm-5.3-flash（也可填写服务端支持的其他编码）
Timeout: 120 秒
```

密钥仅保存在服务端状态目录的 `model_config.json`，文件权限为 0600；接口和前端只返回脱敏值。
拓扑图、截图和印章等任务需要模型支持图片输入；选择纯文本模型时，这些视觉稽核会明确报告模型调用失败。
旧 `secrets.env` 保留用于回滚，但升级后不再读取其中的地址、密钥或模型，也不会自动迁移旧密钥。
如需立即关闭模型说明，只需设置
`AUDIT_LLM_ENABLED=false` 并重启，原有解析和规则稽核流程保持不变。未配置密钥时，
成功提取的项目会提示“AI未配置，已按现有逻辑完成”。

每项 AI 结果保存在 `audits/<稽核编号>/AI复述.json`，并同步显示在详情页和离线
`汇总报告.html`。发送给外部模型的内容会限制为业务判定约束、字段摘要、最多 10 条问题
及大列表最多 5 条样例，单项请求正文不超过 32 KiB；完整原始文档和完整资产大表
不会作为 AI 请求发送。

网页平台与下面的原命令行功能彼此独立，原有单项、批量和 `batch-all` 命令继续可用。

最简单的使用方式是直接把一个系统材料文件夹传给主程序，程序会自动执行全部稽核项：

## 输入单位

一次处理的最小输入不是单个 Markdown，而是一个系统材料文件夹，例如：

```text
互联网部/
└── 中国移动通信集团浙江有限公司管理支撑系统IP认证系统-2/
    └── 2-1-13-2 中国移动通信集团浙江有限公司管理支撑系统IP认证系统定级报告2025.md
```

DJ-02 在 `extractors/dj_02.py` 中规定输入文档名称必须包含 `定级报告`。程序会在系统文件夹内递归查找：

- 恰好一份：将该 Markdown 送入 DJ-02 提取器。
- 没有找到：记为 `missing_document`。
- 找到多份：记为 `multiple_documents`，不会擅自选择。
- 其他名称的 Markdown：不会送入 DJ-02。

DCZ-01～04 使用“系统目录”输入模式，只检查系统解析目录根层的固定标准 Markdown；
不会递归匹配近似名称、历史文件、原始 Word/Excel 或 `文件分析.json`。

## 单个系统处理

```bash
python3 main.py run \
  --item DJ-02 \
  --input-dir "/路径/互联网部/某系统-2" \
  --extracted-output output/DJ-02字段.json \
  --audit-output output/DJ-02稽核结果.json
```

DJ-02 字段输出保存为 `DJ-02.json`，只包含公式输入和声明等级四个字段：

```json
{
  "社会影响力赋值": 2,
  "规模和服务范围赋值": 3,
  "提供服务的重要性赋值": 2,
  "声明安全等级": 2
}
```

稽核规则内部固定使用：

```text
k = Round1{Log2[1/3×2^I + 1/3×2^R + 1/3×2^V]}
```

计算 k 后按照等级区间得到计算等级，最后只比较计算等级与报告声明等级是否一致。

## 完整测试集批量处理

当前测试集结构是 `测试集/部门/系统单位`，因此单位深度默认为 `2`：

```bash
python3 main.py batch \
  --item DJ-02 \
  --dataset-dir "/路径/定级报告解析测试集" \
  --output-dir output/DJ-02_完整测试集
```

终端会按照每个“部门/系统文件夹”分别输出结果，例如 `[DJ-02] ✅ 通过 | 部门/系统` 或 `[DJ-02] ❌ 不通过 | 部门/系统 | 原因：缺少目标文档`。成功行同时显示计算 k、计算等级和声明等级。末尾只提供数量统计，不把整个测试集当成一个业务稽核对象。退出码含义：所有单位成功为 `0`，至少一个单位未成功为 `1`，程序运行错误为 `2`。完整明细仍保存在 `批量处理汇总.json`。

每个系统独立提取和稽核，输出结构如下：

```text
output/DJ-02_完整测试集/
├── 批量处理汇总.json
└── 部门/
    └── 系统单位/
        └── DJ-02/
            ├── DJ-02.json
            └── 稽核结果.json
```

如果其他测试集的系统单位不在第二层，可通过 `--unit-depth` 调整。
如果 `--dataset-dir` 直接指向一个系统材料文件夹，请使用 `--unit-depth 0`，让该目录本身作为唯一系统单位处理。

## 一次运行全部稽核项

`batch-all` 会自动取得所有已成对注册的提取器和稽核规则，逐项执行完整测试集。某一项存在业务不通过、缺文档或程序异常时，仍会继续运行其他稽核项。

```bash
python3 main.py batch-all \
  --dataset-dir "/路径/批量解析结果" \
  --output-dir output/完整稽核结果 \
  --overwrite
```

只对一个系统运行全部稽核项：

```bash
python3 main.py batch-all \
  --dataset-dir "/路径/部门/某系统" \
  --output-dir output/某系统完整稽核结果 \
  --unit-depth 0 \
  --overwrite
```

每个稽核项保存到 `output/完整稽核结果/<稽核编号>/`，总览保存到 `output/完整稽核结果/完整稽核汇总.json`。退出码 `0` 表示全部稽核项的全部单位均通过，`1` 表示存在业务不通过、缺文档等结果，`2` 表示至少一个稽核项发生程序错误。

如果只需要运行完全由代码规则判定、保证整个批次不发起模型请求的项目，增加
`--rule-only`：

```bash
.venv/bin/python main.py batch-all \
  --dataset-dir "/路径/批量解析结果" \
  --output-dir output/纯规则批量结果 \
  --unit-depth 2 \
  --rule-only \
  --overwrite
```

纯规则是默认类型；新增规则只有在注册时显式声明 `uses_model=True`，才会被该模式跳过。
普通 `batch-all` 仍会运行全部项目，但命令行链路不会追加网页使用的统一模型复述：纯规则
直接输出规则结论，只有规则自身确实需要语义或视觉识别时才调用模型。总汇总中的
`execution_mode` 会记录运行模式，`excluded_model_items` 会列出纯规则模式跳过的项目。

### 从原始 Word/Excel/PDF 开始跑完整流程

`batch-all-source` 会先按系统文件夹调用 anydoc，把原始材料解析并标准化为 Markdown，
再对每个系统分别执行全部稽核项。原始材料不会被修改。普通 `batch-all` 仍保持原来的
“稽核项优先”目录结构；`batch-all-source` 使用“系统优先”目录结构：

```text
输出根目录/
├── 解析结果/
│   ├── 系统A/
│   └── 系统B/
├── 稽核结果/
│   ├── 系统A/
│   │   ├── BEAN-01/
│   │   │   ├── BEAN-01.json
│   │   │   ├── 稽核结果.json
│   │   │   └── 批量处理汇总.json
│   │   ├── 其他稽核项/
│   │   ├── 完整稽核汇总.json
│   │   └── 系统稽核汇总.json
│   ├── 系统B/
│   └── 全部系统汇总.json
└── 全流程汇总.json
```

输入根目录包含“部门/系统”两层时，解析结果和稽核结果会原样保留这两层相对路径。

输入目录是“核心网部”这类部门目录时，其直接子目录才是系统，因此使用
`--unit-depth 1`：

```bash
.venv/bin/python main.py batch-all-source \
  --source-dir "/Users/wenxuanzhang/Desktop/网管中心/核心网部" \
  --output-dir "output/核心网部_全流程结果" \
  --unit-depth 1 \
  --rule-only \
  --overwrite
```

全流程完成后，命令会自动读取固定路径
`<source-dir 同级>/<source-dir 目录名>label/ground_truth.v1.json`。
例如上述输入对应：

```text
/Users/wenxuanzhang/Desktop/网管中心/核心网部label/ground_truth.v1.json
```

传输部使用
`/Users/wenxuanzhang/Desktop/网管中心/传输部label/ground_truth.v1.json`。
程序不再扫描或解析 Markdown 真实标签。默认缺少该 JSON 会报错；
只有显式增加 `--skip-evaluation` 才会跳过评估。

`--rule-only` 只影响稽核阶段：原始材料仍正常解析，但不会运行需要模型的稽核项。
移除该参数即可运行包含模型项目的全部稽核项。输入是“网管中心/部门/系统”两层结构时
使用默认的 `--unit-depth 2`；输入本身就是一个系统文件夹时使用 `--unit-depth 0`。

单个系统解析失败不会阻断其他系统；失败系统仍会进入稽核阶段并明确报告缺少文档。
如使用 `--overwrite`，旧的整个全流程结果会先改名备份，避免旧 Markdown 或已下线的
稽核项目录混入本次结果。

命令行汇总使用 `classification` 表示最终结果，只有三个值：

- `passed`：通过。
- `failed`：不通过，包含缺材料、缺章节、提取失败和程序异常。
- `not_applicable`：业务规则明确不适用。

`batch_passed` 和 `all_passed` 仅为兼容旧脚本保留；它们在“不适用”时也为
`true`，因此不能用来区分“通过”和“不适用”。新的读取逻辑应直接看
`classification`。`audit_counts` 固定包含 `passed`、`failed`、`not_applicable`
三个计数。

### 真实标签三分类评估

默认由 `batch-all-source` 在稽核完成后自动评估，无需再运行独立命令。
固定 JSON v1 结构如下：
完整机器可读约束见 `reference_data/ground_truth.v1.schema.json`。

```json
{
  "schema_version": 1,
  "kind": "audit_ground_truth",
  "source_name": "核心网部",
  "scope": "核心网5",
  "items": [
    {
      "item_id": "DJ-01",
      "name": "DJ-01 定级报告：三要素赋值符合标准要求",
      "category": "2.1 定级报告"
    }
  ],
  "systems": {
    "与 batch-all-source unit 完全一致的系统目录名-3": {
      "DJ-01": "passed"
    }
  }
}
```

约束：

- `source_name` 必须与 `--source-dir` 最后一层目录名一致。
- `systems` 的键必须与 `batch-all-source` 产出的 `unit` 完全一致，包括 `-3` 等后缀。
- 每个系统必须包含 `items` 声明的全部稽核项，不能缺少或多出。
- 标签值只能是 `passed`、`failed`、`not_applicable`。
- 标签与程序结果直接比较 `classification`，不再根据中文描述推断。

标注 Excel 可用脚本批量生成各部门的 JSON：

```bash
.venv/bin/python tools/extract_ground_truth_labels.py \
  --xlsx "/路径/定级备案报告-稽核项标注.xlsx" \
  --root-dir "/Users/wenxuanzhang/Desktop/网管中心" \
  --overwrite
```

脚本从“稽核文件/检查项/判定逻辑”表头右侧读取系统列，根据上一行的部门分组
匹配网管中心下的部门与系统文件夹，并原子覆盖
`<部门名>label/ground_truth.v1.json`。系统名会保留磁盘目录中的 `-3`、
`-2025-3` 等后缀。默认延续当前口径排除 `DJ-06`；如需重新导出该项，增加
`--include-item DJ-06`。首次核对可增加 `--dry-run`，只校验映射而不写文件。

中文结论映射为：以“符合/一致/是/通过/正确/齐全”开头为 `passed`；
以“不符合/不一致/不齐全/未识别/无法检测/无法确认/无法判断/不通过/失败/否”
开头为 `failed`；只有明确以“不适用”开头才是 `not_applicable`。遇到空白或
未知结论时整批停止，不产生部分更新。

如果仅需针对已有结果重新评估：

```bash
.venv/bin/python tools/evaluate_batch_results.py \
  --source-dir '/Users/wenxuanzhang/Desktop/网管中心/核心网部'
```

独立命令同样默认读取上述同级固定 JSON。
默认从 `output/<部门名>_全流程结果` 定位已生成的系统稽核结果。如结果位于其他目录，
可另行传入 `--result-dir "/路径/全流程结果"`。
整个评估过程只读取本地 JSON 标签和本地稽核结果，不访问或修改飞书。

程序预测只读取新汇总中的 `classification` 三分类字段：`passed`、`failed`、
`not_applicable` 分别对应“通过”“不通过”“不适用”。不兼容只有
`batch_passed` 的旧汇总；遇到旧汇总会提示重新运行 `batch-all-source`。

`DISPIMG(...)` 标记，就按已有证明内容处理，不要求导出实际图片，也不要求独立证明材料。
其他内容仍复用 FHX-04 的实质内容判断。全部答案说明都有实质内容时直接通过；只有存在
答案说明为空、普通占位文字或“见证明材料”等纯引用的评测项时，才沿用原编号核对逻辑，
要求对应编号出现在同一系统的证明材料中。

避免把“2级”“2048kbit/s”等正文数字误识别为编号末段；未知编号仍会保留用于检查多余项。

## YJYA-01 应急预案与演练报告的演练项目一致

YJYA-01 使用 `应急材料分析.json` 精确读取当前 `应急预案.md` 和
`应急演练报告.md`。预案只从“预案管理名录”的“演练记录”列提取日期最新一行
“开展演练：”后的科目；报告依次尝试“演练科目内容”“演练科目及内容”
“演练项目”三个正文标题。比较时忽略空格、大小写、标点和科目顺序，但不删除
“攻击、事件、演练”等业务词，因此“网页篡改”与“网页篡改攻击”不一致。

## YJYA-02 应急预案包含安全事件定级章节

YJYA-02 只检查 `应急预案.md` 正文中的 Markdown 标题。标题包含
“安全事件定级”即通过，不限制章节号；目录链接和普通正文提及不计入。

## YJYA-03 应急预案包含差异化响应级别

YJYA-03 在排除目录后的预案正文中识别一级至四级响应，兼容中文数字、
ASCII 罗马数字和 Unicode 罗马数字。至少出现两个不同响应级别即通过。

## YLBG-01 二级及以上系统提供演练报告

YLBG-01 复用定级报告“定级方法/安全等级计算方法”章节中的声明安全等级。
一级系统显示不适用；二级及以上系统目录中存在当前标准文件
`应急演练报告.md` 才通过。“上一份应急演练报告.md”不能替代当前报告。

## YLBG-02 每个系统至少一个演练场景

YLBG-02 依次尝试演练报告正文中的“演练科目内容”“演练科目及内容”
“演练项目”标题。标题存在且下方至少提取到一个非空演练科目才通过；目录命中不计入。

## YLBG-03 至少一次勒索攻击应急演练

YLBG-03 只在上述演练科目章节范围内检查“勒索”关键词，兼容勒索攻击、
勒索软件攻击和勒索病毒攻击。报告其他章节中的勒索文字不计入。

## YLBG-04 演练报告五类必要要素

YLBG-04 在排除目录后的报告正文中检查演练目标、演练时间、参加演练人员名单、
演练过程和演练现场照片。时间兼容“演练时间、地点、人员”，人员兼容“参演人员”，
照片章节兼容“演练现场照片记录”“演练现场”“现场照片”。现场照片必须在照片章节
范围内存在图片标记；只有标题或“附上照片”占位文字不通过。

## YLBG-05 演练报告图片均有时间水印

YLBG-05 读取 `应急材料分析.json` 中当前 `应急演练报告.md` 对应的完整图片清单，
不混入上一份报告，也不只检查现场照片章节。每张可读取的真实 JPG/PNG 图片单独调用一次视觉模型，
核对画面内是否存在清晰的日期或时间水印；文件名、EXIF、普通正文日期和图片外图注不算水印。
任意一张缺少水印或无法读取均不通过，并在结果中列出图片序号、图片 ID、文件名和判断依据；
全部图片都有时间水印才通过。外链、无法导出、缺文件和暂不支持格式的真实图片仍会留在清单中并
按“无法检查”处理，不会被静默略过；OLE 等非图片嵌入对象会记录但不冒充图片送入模型。

## YLP-01 基础安全演练计划逐行勾选

解析器识别文件名包含“演练计划”的 `.xls/.xlsx`，沿用 AnyDoc 输出标准
`演练计划.md`。YLP-01 只定位 `基础安全演练计划` 工作表对应的 Markdown 标题，
将“参演系统”非空的记录视为有效计划行，并且只检查“参演系统”之后、
“计划演练时间”之前的恶意程序类、网络攻击类和安全隐患类事件列。

每个有效计划行至少出现一个精确字符 `√` 才通过，多个勾选也通过；日期、完成情况、
备注或其他工作表中的 `√` 不计入。AnyDoc 会遵循 Excel 当前筛选和隐藏状态，因此本项
检查的是 AnyDoc 实际输出的可见计划行，不代表被筛选隐藏的全年记录也已检查。
