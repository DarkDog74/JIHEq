# 浙江移动定级备案报告稽核系统｜项目交接文档

> 本文面向第一次接手项目的开发者。先按本文命令验证环境和现有流程，再修改代码。
> 当前项目根目录示例：`/Users/wenxuanzhang/Desktop/稽核代码2`

## 1. 项目用途

系统从业务系统材料文件夹开始工作：

```text
原始 Word / Excel / PDF / 图片
        ↓
标准 Markdown 和解析 JSON
        ↓
提取器（extractors）
        ↓
稽核规则（audit_rules）
        ↓
通过 / 不通过 / 不适用
        ↓
可选的 LLM 说明和前端展示
```

每个稽核项通常由两份代码组成：

| 目录 | 作用 |
|---|---|
| `extractors/<item>.py` | 从 Markdown 或标准化材料中提取客观字段 |
| `audit_rules/<item>.py` | 根据字段执行业务判定 |
| `core/audit_catalog.py` | 稽核项目录、分组和启用状态 |
| `core/batch_process.py` | 批量处理核心实现 |
| `main.py` | CLI 总入口和全流程编排 |
| `core/` | 核心实现模块 |
| `parsing_engine/` | 从原始文件调用解析器 |
| `parser/` | AnyDoc、Word/PDF/Excel 和应急材料标准化 |
| `platform_app/` | 本地 Web 服务、前端任务和 AI 说明 |
| `tools/` | 标签提取、Label 评估和 Token 基准脚本 |
| `docs/` | 交接文档、业务规则记录等项目文档 |
| `config/paths.json` | 可迁移路径、LibreOffice 和 MinerU 地址配置 |
| `tests/` | 单元测试和批处理测试 |

### 1.1 路径配置

机器相关路径统一放在 `config/paths.json`。相对路径以项目根目录为基准，环境变量
（例如 `AUDIT_EVALUATION_ROOT`、`AUDIT_MINERU_URL`）优先于配置文件。当前已整理的
配置项包括：评估集根目录、默认输出目录、解析脚本示例源目录、虚拟环境目录、
LibreOffice 候选路径和 MinerU 接口地址。主流程的输入与输出仍优先使用命令行参数。

当前 `ZM-01` 在目录中保留代码，但在 `core/audit_catalog.py` 中被禁用，不计入正式稽核项分数。

## 4. CLI 稽核命令

### 4.1 单个稽核项：只提取

```bash
.venv/bin/python main.py extract \
  --item DJ-02 \
  --input-dir "/路径/某业务系统-2" \
  --output "/路径/结果/DJ-02.json" \
  --overwrite
```

### 4.2 单个稽核项：只判定

```bash
.venv/bin/python main.py audit \
  --item DJ-02 \
  --input "/路径/结果/DJ-02.json" \
  --output "/路径/结果/DJ-02-稽核结果.json" \
  --overwrite
```

### 4.3 单个稽核项：提取并判定

```bash
.venv/bin/python main.py run \
  --item DJ-02 \
  --input-dir "/路径/某业务系统-2" \
  --extracted-output "/路径/结果/DJ-02.json" \
  --audit-output "/路径/结果/DJ-02-稽核结果.json" \
  --overwrite
```

### 4.4 Markdown 测试集运行一个稽核项

```bash
.venv/bin/python main.py batch \
  --item DJ-02 \
  --dataset-dir "/路径/批量解析结果" \
  --output-dir "/路径/output/DJ-02-完整测试集" \
  --unit-depth 2 \
  --overwrite
```

`--unit-depth` 含义：

- `2`：测试集根目录下是“部门/系统”；
- `1`：部门目录下直接是系统文件夹；
- `0`：输入本身就是一个系统目录。

### 4.5 Markdown 测试集运行全部稽核项

```bash
.venv/bin/python main.py batch-all \
  --dataset-dir "/路径/批量解析结果" \
  --output-dir "/路径/output/批量稽核结果" \
  --unit-depth 2 \
  --overwrite
```

只运行纯规则项、完全不调用模型：

```bash
.venv/bin/python main.py batch-all \
  --dataset-dir "/路径/批量解析结果" \
  --output-dir "/路径/output/纯规则结果" \
  --unit-depth 2 \
  --rule-only --overwrite
```

### 4.6 从原始 Word/Excel/PDF 开始的完整流程

这是最接近实际使用的命令：先解析原始材料，再按系统执行全部稽核，并在同级 Label 目录存在时评估。

```bash
.venv/bin/python main.py batch-all-source \
  --source-dir "/Users/wenxuanzhang/Desktop/网管中心/网管支撑部" \
  --output-dir "output/网管支撑部_全流程结果" \
  --unit-depth 1 \
  --overwrite
```

跳过 Label 评估：

```bash
.venv/bin/python main.py batch-all-source \
  --source-dir "/路径/部门目录" \
  --output-dir "/路径/结果目录" \
  --unit-depth 1 \
  --skip-evaluation \
  --overwrite
```

只解析原始材料并执行纯规则稽核：

```bash
.venv/bin/python main.py batch-all-source \
  --source-dir "/路径/部门目录" \
  --output-dir "/路径/纯规则全流程结果" \

  --overwrite
```

## 5. 输出结果怎么看

### 5.1 系统级汇总

每个系统都有独立目录：

```text
结果根目录/稽核结果/<系统名>/系统稽核汇总.json
```

常用字段：

- `classification`：系统整体三分类结果；
- `all_passed`：是否全部适用稽核项通过；
- `audit.counts.passed_items`：通过项数量；
- `audit.counts.failed_items`：不通过项数量；
- `audit.counts.not_applicable_items`：不适用项数量；
- `audit.counts.execution_errors`：程序错误数量；
- `audit.items`：每个稽核项的明细。

### 5.2 单项结果

```text
结果根目录/稽核结果/<系统名>/<稽核编号>/批量处理汇总.json
结果根目录/稽核结果/<系统名>/<稽核编号>/稽核结果.json
结果根目录/稽核结果/<系统名>/<稽核编号>/<稽核编号>.json
```

看三分类时，以单项的 `classification` 为准：

- `passed`：通过；
- `failed`：不通过；
- `not_applicable`：不适用。

`batch_passed: true` 只表示该批次全部通过，不适合查看单项原因。缺材料通常也会归入 `failed`，具体原因看 `reason_code`、`message` 和 `issues`。

### 5.3 标签评估

标签评估文件通常为：

```text
结果根目录/<部门>/评估结果/评分汇总.json
结果根目录/<部门>/评估结果/评分汇总.md
```

重点字段：

- `totals.correct_items`：三分类与 Label 一致的数量；
- `totals.incorrect_items`：三分类与 Label 不一致的数量；
- `totals.scored_items`：实际计分项数量；
- `totals.accuracy`：一致率；
- `coverage.truth_only`：Label 有、程序未输出的项；
- `confusion_matrix`：按“真实标签 → 程序标签”统计。

不要把“程序判为不通过的数量”写成“错误数量”。前者是业务分类，后者只有在与人工 Label 不一致时才成立。

## 6. 当前稽核项开发约定

新增或修改稽核项时，保持以下边界：

1. 提取器只提取事实，不在提取器中直接做业务判定。
2. 规则只使用提取字段，不直接读取原始文件。
3. 不为单个系统名、固定行号或单个样本写特例。
4. 缺文档、无目标章节、结构异常、业务不通过必须使用不同原因码。
5. 新规则必须同时增加正常、反例、缺字段、格式差异和批量输出测试。
6. 改规则前先保存旧结果；修改后必须跑单元测试和代表性批量测试。
7. 业务结论以规则为准，LLM 说明不能改写通过、不通过、不适用。

## 9. 常见问题排查

### “只有一个系统”或系统被混在一起

检查 `--source-dir`、`--dataset-dir` 和 `--unit-depth`。原始部门目录一般用 `--unit-depth 1`，测试集“部门/系统”一般用 `--unit-depth 2`。确认输出中是否存在每个系统独立的 `系统稽核汇总.json`。

### “完整稽核”显示失败

先区分：

1. `failed_items`：业务不通过；
2. `missing_document`：缺材料，按当前口径也属于不通过；
3. `extraction_error`：字段解析异常；
4. `execution_error`：程序异常。

不要只看 `all_passed: false`，要继续看 `audit.items`。

### 模型没有调用或说明失败

检查网页模型配置、模型是否支持图片、`AUDIT_LLM_ENABLED` 是否为 `false`，再查看 `platform_app/ai_service.py` 生成的 AI 结果。AI 说明失败不应改变业务稽核三分类。

### 重新运行是否覆盖旧结果

带 `--overwrite` 时，程序会先把原输出目录改名为带时间的旧结果备份，再生成新结果。不要手动删除旧目录作为第一选择。

### 如何确认改动没有污染结果

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -s tests -q
.venv/bin/python main.py list > /tmp/audit-list.json
```

然后对一个通过系统、一个不通过系统和一个缺材料系统分别重跑，核对三分类、原因码和字段 JSON。
